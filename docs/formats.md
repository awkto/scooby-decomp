# Asset formats: graphics compression, palettes, tilemaps

Status: these notes come from VDP write traces of the boot sequence, the title screen and the
Lobby (GPGX harness, see "Tracing" below), plus reading the 68k code. Every format described
here is checked by `tools/py/gfx.py`, which rebuilds the screens from ROM data alone. ROM
ranges are in `data/assets.txt` (generated by `gfx.py assets`).

All addresses are ROM offsets (= 68k addresses) unless they start with `$FF` (work RAM) or are
called VRAM/CRAM.

## How graphics reach the VDP

Nearly everything takes one of two routes:

1. ROM → decompressor → RAM buffer → VRAM. The buffer is usually `$FF4000` (LZSS) or
   `$FF3000` (RLE). The buffer is then written to the data port by `loc_00992C`, or DMA'd by
   `loc_0099F6`.
2. ROM → VRAM directly, uncompressed: nametable rows through `loc_00992C`, single words
   through `loc_009964`.

VDP helper routines:

| addr | purpose | args |
|---|---|---|
| `$00992C` | CPU copy to VRAM | d0 = VRAM addr, a0 = src, d1 = word count |
| `$009964` | write one VRAM word | d0 = VRAM addr, d1 = value |
| `$0099F6` | VRAM DMA from 68k bus, split at 128 KiB boundaries; calls `$009A3C` | a0 = src, d0 = VRAM dest, d1 = words |
| `$009B10` | CRAM DMA | same args as `$009A3C` |
| `$009BE4` / `$009C1E` | fill VRAM / CRAM with a word | d0 = addr, d1 = count, d2 = value |
| `$009C58` / `$009C5E` | clear VRAM / CRAM | d0 = addr, d1 = count |
| `$009E7E` | fade the 64-word palette at a0 into CRAM: 8 steps, target buffer `$FF06F8` DMA'd each frame | a0 = 128-byte CRAM image |
| `$00974C` / `$009742` | wait 1 / d0+1 VBlanks | |

Palettes always go through the RAM copy `$FF06F8` (current) / `$FF0778` (target) and reach
CRAM by DMA from `$FF06F8`. As a result, CRAM never reads from ROM directly in the traces.

## Compression format 1: LZSS (`$0097AA`)

`a0` = compressed stream, `a1` = 4 KiB ring buffer (the game always passes `$FF3000`),
`a2` = output. On return, `(a1).l` holds the decompressed size. The routine saves and restores
every register.

* The bitstream is MSB-first over big-endian data, starting at `a0`. The 68k pre-loads one
  long, then refills 16 bits at a time; logically it is a plain continuous bitstream.
* Each token starts with a flag bit:
  * `1`: an 8-bit literal. Output it and also store it in `ring[r++]`.
  * `0`: a 12-bit ring position `P`. **`P == 0` ends the stream.** Otherwise a 4-bit `L`
    follows. Copy `L + 2` bytes from `ring[P], ring[P+1], …` (mod 4096) and store each byte in
    the ring as well.
* The ring write index `r` starts at **1**, and indices wrap at 4096. The ring is never
  cleared. No stream checked so far reads an unwritten slot, so `gfx.py` starts with a zeroed
  ring.

This is classic Okumura-style LZSS (N=4096, F=17, THRESHOLD=1) with a 1-bit flag per token
instead of flag bytes, and position 0 used as the end marker. In ROM, each room asset stream is
preceded by a big-endian `u32` holding its packed length. The loader skips it with
`tst.l (a0)+`.

Verified: the Lobby tiles (`$11CB6E` → 0x6200 bytes) are byte-identical to VRAM
`$0000-$61FF` in the emulator. The three Lobby name tables match the VRAM nametable words.
All 51 rooms of both mysteries decompress to exactly `w*h*2` bytes of names.

## Compression format 2: RLE / PackBits variant (`$009C64`)

`a0` = stream, `a2` = output. Used by the title screen.

```
u32 unpacked_size
repeat until unpacked_size bytes have been produced:
  c = next byte
  c in 0x00..0x7F : copy the next c+1 bytes
  c in 0x80..0xFF : repeat the next byte ((-c) & 0xFF) + 1 times   (0xFF -> 2, 0x80 -> 129)
```

The 68k code fills the runs with long writes and then rewinds `a2`, so it may overwrite up
to 3 bytes past the run (harmless). It also sets VDP register 12 bit 3 (shadow/highlight)
while it runs if `$FF09ED` bit 3 is set. That is a side effect, not part of the format.

Verified: the title-screen font streams (`$016D38` → VRAM `$B900`) and the plane-A animation
frames match VRAM.

## Tiles, names, palettes

These are standard Mega Drive formats:

* **Tiles:** 8×8 at 4 bpp, 32 bytes, high nibble = left pixel.
* **Name (nametable) word:** `p cc v h nnnnnnnnnnn` (priority, palette 0-3, vflip, hflip,
  tile index).
* **Palette word:** hardware CRAM format `0000 BBB0 GGG0 RRR0`. CRAM images in ROM are 64
  words (4 palettes × 16 colours). Colour 0 of each palette is transparent.
* **Colour levels:** `gfx.py` maps the 3-bit levels to 0,36,73,…,255. GPGX's RGB565 output
  uses 0,32,64,96,136,168,200,232 for R/B (G slightly different).
  `tools/py/cmpshot.py` compares images in 3-bit level space, so this difference doesn't matter.

## Rooms

Everything in this section is dumped in readable form by `tools/py/gfx.py roomdump [--world N] [--room N]`
(every header field, all objects, the hotspot/overlay table, and for each room its record, scripts,
row table, entry points, spawn points and waypoints). The loader is decompiled in
`port/src/game/room.c`; see also `docs/subsystems/room.md`.

### Mystery ("world") headers

`$031AF2` holds 2 longs: the header pointers for mystery 0 (`$0FCA0C`, Blake's Hotel) and
mystery 1 (`$0FCA40`, Ha Ha Carnival). The index is in `$FF06AA`. The active header pointer
is kept in `$FF068E`. Every header field is an absolute long (names as in `gfx.py World`):

| off | name | meaning |
|---|---|---|
| +00 | state_start | initial game-state block (copied to `$FF2A00` until +04 by `game_state_init` `$007F22`; RAM is zeroed for 256 bytes first) |
| +04 | objects | **object init records** (see "Objects"): from here to +08. Also the end of the state block |
| +08 | rooms | room table, 0x14 bytes per room, indexed by (room − 2) |
| +0C | tiles_base | base for the room-entry tile offsets (the room table ends here) |
| +10 | maps_base | base for the room-entry map-pack offsets |
| +14 | palettes | per-room palettes, 128 bytes per room, indexed by (room − 2) |
| +18 | item_icons | 0x182-byte records indexed by `object.word(+4) − 1`; read by `$005D1C` for the objects in the inventory (icon tiles; layout not decoded) |
| +1C | overlay_base | base for the offsets in the overlay pointer table (+24) |
| +20 | names_base | base for string offsets: room names, object names, dialogue |
| +24 | overlay_ptrs | table of u32 offsets (+ overlay_base) to **tile overlay records**; 211 entries in mystery 0 (see "Overlays and hotspots") |
| +28 | object_tbl | 8-byte record per object, in object order: `u32 script_off` (+ scripts_base), `u32 name_off` (+ names_base) |
| +2C | scripts_base | base of all script data (bytecode of the script interpreter at `$0020xx`) |
| +30 | start_room | pointer to `{u16 room, u16 music, u16 script_len, script...}`: initial room (→ `$FF06AC`), music id (→ `$FF06A6`) and the intro script run by `$0013BA` |

The number of rooms is `(tiles_base − rooms) / 0x14`: 21 rooms in mystery 0, 30 in mystery 1.
Room numbers (as stored in `$FF06AC`) start at 2; **room 1 means "inventory"** and room 0 "nowhere" in
an object's room field.

### Room entry (0x14 bytes)

| off | meaning |
|---|---|
| +00 | name offset (+ header `names_base`); the loader stores the absolute pointer in `$FF06D2` |
| +04 | tile offset (+ `tiles_base`): `u32 packed_len` followed by an LZSS stream; output goes to VRAM `$0000` |
| +08 | map-pack offset (+ `maps_base`) |
| +0C | offset (+ `scripts_base`) of the **load script**: run at the end of the room load (`$00221A`) while the screen is still dark, before the palette fade |
| +10 | offset (+ `scripts_base`) of the **arrival script**: run by `$002278` after the fade-in |

Both scripts start with two words `{u16 len, u16 ?}`; the script interpreter (`script_run_frame`)
gets `a5` = data after the 2 words and `a6 = a5 + len`, i.e. a data section of `len` bytes
followed by the opcode stream (many rooms have an almost empty script, e.g. the Lobby's two are 4 bytes apart). Script opcodes `$11` (`script_op_11`) and `$18`
(`script_op_18`) change room: they store `room`, `ram_5b8` and the entry point number × 4 (`$FF069E`),
then call the room change (`$002196` / `$002138`).

### Map pack

```
u16 width, u16 height      (cells, e.g. Lobby 64 x 19; copied to $FF06C6/$FF06C8)
u32 len1, LZSS[len1]       plane B names  (width*height words) -> RAM $FF7000, copied to $FFA800
u32 len2, LZSS[len2]       plane A names                      -> RAM $FF8C00, copied to $FFC400
u32 len3, LZSS[len3]       zone map (see below)               -> RAM $FFE000
...                        post-zone data (see below), pointer kept in $FF0692
```

The copies at `$FFA800`/`$FFC400` are pristine; `$FF7000`/`$FF8C00` are the working copies that
overlays modify and that the scroller reads. (`room_load` copies a constant 0x1800 words for plane A, not
the unpacked length; plane B uses the real length. Harmless: the area is overwritten later.)

In the Lobby, plane B words use palette 2 with priority clear, and plane A words use palette 3
with priority set. Across all 51 rooms, both planes mix palettes 0-3 and both priorities, and
plane A is empty in 10 rooms. `gfx.py` therefore composites in VDP order: B low, A low, B high, A high.

**Zone map** (width × height words, one per 8×8 cell, `$FFE000`): bit 15 is a flag (the actor mover at `$007396`
tests the sign to set a bit in `$FF0ABB`); bits 0-14 are an index. Index 0 = no collision. Otherwise
`dat_02AF8E[index]` (`$02AF8E`, one word per index) holds `bits 0-10 = collision-mask tile number`,
`bit 11 = do NOT mirror x`, `bit 12 = mirror y`; the mask tiles are 4bpp tiles in the shared table
`dat_02B0BA` (32 bytes each). The pixel (x & 7, y & 7) of the cell is looked up in the (flipped) mask: a non-zero
nibble means solid. So walkability is pixel-exact: `$0073D6` (probe at the cursor `$FF0642/$FF0646`) and
`$007476` (probe at `$FF064A/$FF064E`) return the masked nibble in D5 (Z = free).

### After the zone map

`room_load` leaves `$FF0692` pointing at the first byte after the third LZSS stream. What follows (all
words big-endian, coordinates in 8×8 cells):

| offset | size | meaning |
|---|---|---|
| +0 | `height` words | per-map-row table: `$FFFF` = none, otherwise a small value (e.g. Basement rows 0/2 = 9, Lobby rows 0/7/18 = 12/8/0). Read by the actor path code at `$007168`, which finds the nearest marked row above and below an actor. Exact meaning (walk limit / depth line?) not pinned down |
| +2h | 8 × `{u16 x, u16 y}` = 0x20 bytes | **entry points** (`$FF0696`): where Shaggy appears. Scripts select one with `$FF069E` = number × 4 (`room_load` writes x×8, y×8 to `$FF04DC`/`$FF04F4`, y−1 to the previous-y word). Unused slots are 0,0. Camera: x − 16, y − 10 cells, clamped to the map (32 × 19 cell window) |
| +2h+0x20 | up to 8 × `{u16 w0, u16 y}`, terminated by `$FFFFFFFF` | **spawn points** (`$FF069A`; count in `$FF06A0`). `w0 & $FFF` = x, `y` = y (cells); `w0 >> 14` and `(w0 >> 12) & 3` select two small values (facing / type). The main loop (`$000DEA`) picks one at random every 100 frames (`$FF0688`) and starts something there through `$0056B0` (a roaming enemy/event; not confirmed) |
| +2h+0x40 | 2 × `{u16 x, u16 y}` | **waypoints** (`$FF069A + 0x20`). Used by the click-to-walk code (`$005002`...`$00532A`): when the straight line to the target is blocked, the path goes through waypoint 0 or 1. All zero when the room has none. Rooms with a diagonal stair/ramp have them (Basement (23,8) and (33,14)) |

The next room's map pack follows immediately after the waypoints (its first word is that room's width).

### Objects

The hotspots, items, characters and scenery pieces of a mystery are one flat table of **objects**
(181 in mystery 0). The ROM init records between header +04 and +08 are expanded by
`object_table_init` (`$007F66`) into 0x1A-byte RAM records at `$FF1200 + 0x1A*i`; `$FF06F4` holds the last
index. ROM record (14 bytes, 18 when flag `$0200` is set):

| ROM off | RAM off | meaning |
|---|---|---|
| +00 | +00 (word) | **overlay id** currently shown for the object: 0 = nothing, else the index+1 into the overlay table. bit 15 = restore the original tiles, bit 14 = clear this field afterwards (`$007C04`) |
| +02 | +02 (word) | **type id**. For scenery/hotspots (flag bit1 clear) it is the overlay-record index+1 whose rectangle is the hotspot. For actors (bit1 set) it selects a sprite definition in the 36-entry table `$032670` (sizes in `$0325E0`) |
| +04 | +04 (word) | inventory icon record + 1 (header +18; 0 = none; non-zero only for takeable items: Goblet `$27`, Crumpled Note `$22`, ...) |
| +06 | +06 (word) | **room** the object is in (0 = nowhere/not yet, 1 = inventory, ≥ 2 = room number). Scripts move objects by writing this |
| +08 | +08 (word) | class (0..3; people 0, scenery 1-2, ...) — meaning not decoded |
| +0A | +16 (word) | `$0A0A` normally; `$050A`/`$030A` for doors and similar — not decoded |
| +0C | +18 (byte) | flags: bit0 = in the current room (set by `room_load`), bit1 = **actor** (has a position, drawn as a sprite), bit2 = timer expired / script pending (the main loop runs the object's script `object_tbl[i].script_off`), bit3 = ? (actors only) |
| +0D | +19 (byte) | replaced with `$FF`; later holds the actor slot (0..3) |
| +0E (only if bit1) | +12/+14 (words) | initial x, y in pixels |
| – | +0A (word) | countdown timer, −1 = off; `$007C04` decrements it each frame; the frame it passes 0 it sets flag bit2 (and keeps it set until the script ran) |

Objects 0 and 1 (blank names) are probably Shaggy and Scooby; 2.. are the characters, then items and hotspots in
room order (see the dump). Names come from `object_tbl[i].name_off + names_base` (`'Door'`, `'Stairs'`, `'Mailbox'`...).
Player slots: the position arrays at `$FF04DC` (x) and `$FF04F4` (y) hold 6 longs — slot 0 = Shaggy,
slot 1 = Scooby (the existing name `ram_shaggy_x_prev` at `$FF04E0` is actually Scooby's x, which `room_load`
sets to Shaggy's), slots 2..5 = the actors of the room.

### Overlays and hotspots

Overlay record (`hdr+0x24` pointer table, offsets from `hdr+0x1C`; 211 in mystery 0):

```
u16 x, y, w, h        rectangle in map cells
u16 dx, dy            pixel anchor used by scripts (added to the position they set)
u16 plane             0 = plane B ($E000), non-zero = plane A ($C000)
u16 names[w*h]        replacement nametable words
```

`$007D54` draws an overlay into the working plane copy and into VRAM (patching only the visible part of the
64-wide plane); with the `$FF09EB` bit0 set it DMAs rows instead. With id bit 15 set it copies the *pristine* names
back (restoring the background). Used for doors that open, items that disappear, lit fireplaces...

The same rectangle is the **hotspot**: `$0012CC` runs after every walk step; for every non-actor
object with `room == current room` and `type != 0` it tests whether Shaggy's cell `(x>>3, y>>3)` lies in
the rectangle of overlay `type`; the last hit becomes the current target id (`$FF06AE` = object index + 3), which makes
the verb bar show the object's name.

### Palettes

* CRAM palettes 0-1 come from `$032480` (32 words). They are shared by all rooms and hold
  the UI, Shaggy and Scooby colours. `room_load` stages them in the fade target `$FF0778`.
* CRAM palettes 2-3 are `palettes + (room−2)*128 + 0x40` (32 words), copied to `$FF07B8`
  (= `$FF0778 + 0x40`, so together they form the 64-word target image).
* The first 0x40 bytes of each 128-byte per-room block are not used by the load path traced
  here. They may be alternative palettes for lights off or a fade.

### Room loader sequencing

`script_op_11/18` (or the title code) → `$002196` change room → `$002138` → **`room_load` `$00758A`**:

1. `$002138` first does `sr = $2700`, `pad1 = $FF`, clears VBlank flag bit 3. Interrupts stay off for the whole
   of `room_load`, so no frame is rendered while VRAM is being rebuilt. All VRAM writes are CPU writes through the
   data port; **no DMA is used by the loader** (DMA is used later by the per-frame sprite/SAT/palette code).
2. `room_load`: clear VRAM (64 KiB); reset camera and scroll; stage the shared palettes in `$FF0778`;
   flag objects in this room; copy the room's palettes 2-3 to `$FF07B8`.
3. Decompress the tiles (LZSS) to `$FF4000`, write them to VRAM `$0000` (size at `$FF3000`, minimum 0x400). Right after
   them (`VRAM = size`) `font_tiles_load` `$007A2A` writes the 94 text-font tiles (`$030F12`, recoloured: glyph colour 15,
   background colour 1, base word kept in `$FF068C`, UI tile base in `$FF0802`). Then the UI font (LZSS `$030916`), the raw
   UI tile blocks `$031AFA` (0x40 words), `$031B7A` (0xC0 words), `$031CFA` (0x80 words) and a solid tile of `$1111`.
   The tile-base words go to `$FF06E4/E6/E8`, `$FF08B8`, `$FF068A`. (The address after the 0xC0-word block advances by only 0xC0 bytes, so
   the next block overwrites its second half; the game lives with it.)
4. Window plane `$D000` filled with the blank UI tile; verb bar names `$030016` (6 rows × 61 words + 3 pad words)
   written to `$AA80` with the tile base added.
5. `$005D1C` / `$005CB6` (portrait and inventory VRAM areas, DMA'd), and `$0047AC` (verb-bar text) when the game state bit 1 or `$FF09DE` bit 2 is set.
6. Map pack: decompress plane A, plane B (copy to the pristine buffers), zone map; read the post-zone tables.
7. Place Shaggy (unless `$FF09DE` bit 3), compute the camera, `room_draw_view` `$007950` writes the 32 × 19
   window to both planes (CPU writes, 2 × 608 words) and calls the scroll helpers `$00FC3A/$00FD5E/$00FE74/$00FF68`; then
   `room_setup_actors` `$007A8C` initialises the actor slots (see room.c).
8. Back in `$002138`: flags set, interrupts on, `$005B92`, `$00B0B8` (uploads the sprite tiles of the actors via
   the buffers `$FF3000`/`$FF3800`, one burst per frame until `$FF0AB6` clears), then the **load script** (`$00221A`).
9. `$00219A` (the second half of `$002196`): `palette_fade` fades CRAM from black to `$FF0778`
   over 8 steps (the VBlank handler DMAs `$FF06F8` to CRAM every frame), then the **arrival script** (`$002278`).


### Room screen layout at runtime (Lobby, H32 = 256×224)

| lines | content | how |
|---|---|---|
| 0-15 | room name ("The Lobby") | window plane `$D000` (VDP reg 18 = `$02`: 2 rows from the top) |
| 16-167 | room background, 32×19 cells visible | plane A `$C000` + plane B `$E000`, hscroll = `$FF07F8`/`$FF07FA` (= −camera x), vscroll = `$FF07FC`. These are written by `loc_00FC0A`. |
| 168-223 | verb bar (TAKE LOOK … USE) | HInt handler `$01006C` busy-waits for line 167, then points both planes to `$A000`, sets hscroll = `$FF0800` and vscroll 0 |

Other VRAM areas: SAT `$D800` (DMA from `$FF0008` every frame), hscroll table `$DC00`, and
sprite tiles `$F000-$FEFF`. Sprite tiles are streamed from the RAM buffers `$FF3000` and
`$FF3800` every few frames. `$FF4800` is also DMA'd every few frames to `$A300-$AA7F`, which
is rows 6-20 of the `$A000` plane. Its purpose is unknown: those rows are not on screen in
the bottom band.
Sprite graphics: see "Actor sprites" below.

Lobby specifics: mystery 0, room 16, 64×19 cells (512×152 px). After the start route, the camera
is at x = 160 (`$FF07F8` = `$FF60`).

## Actor sprites

Code: `port/src/game/sprite.c` (functions in `docs/subsystems/sprite.md`). Decoder and renderer:
`tools/py/gfx.py sprite` (writes PNG sheets; see the end of this section).

### Slots

Six actor slots: 0 Shaggy, 1 Scooby, 2-5 the actors of the room (assigned by `room_setup_actors`).
Each slot owns a RAM staging buffer and a VRAM tile area:

| slot | RAM buffer (`$0FC9F4`) | VRAM (`$0FC860`) | tile index |
|---|---|---|---|
| 0 | `$FF3000` | `$F000` | `$780` |
| 1 | `$FF3800` | `$F780` | `$7BC` |
| 2 | `$FF4000` | `$9B00` | `$4D8` |
| 3 | `$FF4800` | `$A300` | `$518` |
| 4 | `$FF5000` | `$9380` | `$49C` |
| 5 | `$FF5800` | `$8C00` | `$460` |

(The `$FF3000`/`$FF4000` buffers are also the LZSS ring and room decompression buffers during a room load.)

### Animation sets

`$032670` holds 36 longs: the animation set of each sprite type (object `+$02` for actors). Set 0
(`$032700`) is Shaggy and set 1 (`$0642D0`) Scooby; `actors_init` `$00801A` puts them in slots 0/1.
All offsets inside a set are relative to the set's address.

```
+0  u16 kind          1 = Shaggy, 2 = Scooby, 3.. = the index+1 in $032670 (mostly)
+2  u16 anim_table    -> u16[n_anims] offsets of the animation scripts
+4  u16 frame_table   -> u16[n_frames] offsets of the frame headers (not used by the code
                         found so far; the scripts point at frames directly). It ends where the
                         first script starts, and the anim table ends at frame_table.
+6  u16 ?             (just before the first frame's RLE data; meaning unknown)
```

Shaggy: 116 animations, 359 frames. Scooby: 86 animations, 260 frames. Animation numbers used by the
walking code: 0-3 walk right/left/up/down, 4-7 stand, `$20`-`$23` bored (docs/subsystems/walking.md).

### Animation scripts

A script is a list of `{u16 op, u16 arg}` pairs, run by `actor_animate` `$00B0B8` whenever the slot's
timer `$FF0618+2i` is ≤ 0 (`actor_dma` decrements the timers in VBlank):

| op | name | effect |
|---|---|---|
| 2 | frame | show the frame whose header is at `arg`; timer = delay; **yield** |
| 3 | goto | continue at `arg` (loops). With the slot's `$FF0AC3` bit ("path once") set: clear it and act like op `$0D` |
| 4 | delay | frames per animation frame (`$FF050C+2i`) |
| 5 | wait | timer = `arg`; **yield** |
| 6 | move | actor x += (s8)low byte, y += (s8)high byte (pixels) |
| 9 | end | set `ANIM_DONE` (`$FF0ABC` bit i); the script stops (the last frame stays) |
| `$0D` | anim | animation number `$FF0488+2i` = `arg`, clear `ANIM_LOOPED`; the script continues |
| `$11` | sound | `sound_play(arg)`, or `sound_stop(arg & $7FFF)` when bit 15 is set |
| other | | ignored |

A new animation is requested by writing `$FF0488+2i` and setting bit i of `$FF0AB5`; the script restarts
at `anim_table[n]` once the previous frame has left the decode pipeline. Example, Shaggy animation 0 (walk
right): `delay 6`, 8 × `frame`, `goto` back to the first frame.

The animation of an off-screen actor (hot spot more than 80 px outside the view) does not advance,
except Scooby's.

### Frame header (14 bytes)

```
+0  s16 hot spot x   (pixels from the frame's left edge: the actor's feet)
+2  s16 hot spot y
+4  u8  width   ($20, $30, $40, $50, $70)
+5  u8  height  ($30, $40, $50)
+6  u32 offset of the frame's RLE stream (+ set address)
+A  u16 sprite attribute bits ORed into every piece: palette (bits 13-14), bit 11 = h-flip
+C  u16 ? (0 or 1)
```

In follow mode (`$FF09E8` bit 3, script sub-op `$15`) the words at `+$0E/+$10` (the next header's hot spot)
of Shaggy's current frame give the attachment point of the partner actor.

### Frame data

One RLE stream (format 2 above). Its unpacked size tells the kind:

* `w*h/2` bytes: **4bpp tiles in piece order**, decoded straight into the slot buffer (most room actors);
* `w*h` bytes: **chunky pixels**, one byte (0-15) per pixel, row-major. Shaggy, Scooby and the sets
  6, 9, 14, 16 use this. These actors are "depth-scaled" (`$FF0AB8` bit i): the stream is decoded to
  `$FF6000` and the scaler writes the tiles.

### Depth scaling

The scale is the slot's depth `$FF05A0+2i` (x) / `$FF05AC+2i` (y), 0 = full size, set from the room's per-row
depth table by `actors_update` (docs/subsystems/walking.md). `$00C3F0 + depth*16` holds 8 words of keep
bits (MSB first): bit set = keep that column (x mask, 3 words for 48 px / 5 for 80 px) or row (y mask).
Depth 0 keeps all. The scaler (`$00D468` for 48×80, `$00DA6A` for 80×48) keeps the marked rows and
columns, packs them to the top left, and fills the rest with colour 0. Each 8-pixel group of an output row
is one long, stored at `buffer + table[row*groups + group]` (tables `$00BC70` for 48×80 and `$00C030` for
80×48: they map the raster onto the column-major tiles of the pieces). `$00D3F0`/`$00D42C` do the same
without scaling; they are used instead when `$FF09E9` bit 3 is set and the scaled hot spot y is below 2.

Because the picture shrinks towards its top left, the hot spot is scaled too:
`hot_x' = (hot_x * (256 - depth_x) & $FFFF) >> 8` (h-flipped frames: `w - ((w - hot_x) * (256 - depth_x) & $FFFF) >> 8`),
`hot_y'` likewise. They are stored at `$FF04AC+2i` / `$FF04B8+2i`.

### Pieces

A frame is drawn as several hardware sprites. The layout depends only on the size (tables `$0FC86C`-`$0FC9EC`:
x deltas, x deltas when flipped, y deltas, tile offsets, SAT size words):

| size | tiles | DMA words | pieces (x, y, cols×rows, first tile) |
|---|---|---|---|
| 112×64 (`$70`) | 112 | `$700` | (0,0) 4×4 @0, (32,0) 4×4 @16, (64,0) 4×4 @32, (96,0) 2×4 @48, then the same at y 32 @56.. |
| 64×64 (`$40`) | 64 | `$400` | 2×2 pieces of 4×4: @0, @16, @32, @48 |
| 48×80 (`$30`) | 60 | `$3C0` | (0,0) 4×4 @0, (32,0) 2×4 @16, (0,32) 4×4 @24, (32,32) 2×4 @40, (0,64) 4×2 @48, (32,64) 2×2 @56 |
| 80×48 (other) | 60 | `$3C0` | (0,0) 4×4 @0, (32,0) 4×4 @16, (64,0) 2×4 @32, (0,32) 4×2 @40, (32,32) 4×2 @48, (64,32) 2×2 @56 |
| 32×80 (`$20`, h `$50`) | 40 | `$280` | (0,0) 2×4 @0, (16,0) 2×4 @8, (0,32) 2×4 @16, (16,32) 2×4 @24, (0,64) 2×2 @32, (16,64) 2×2 @36 |
| 32×other | 32 | `$200` | six 4×4 pieces stacked at y 0..160 (tiles 0,0,0,0,0,16), y −76: looks unused |

Tiles inside a piece are column-major (hardware sprite order). When the frame's attribute bit 11 is set
the pieces are mirrored with the "flipped" x deltas and the VDP flips each piece.

### From script to screen

```
actor_animate (main loop)                     actor_dma (VBlank)                 sprite_build (VBlank)
 op frame: tiles frame -> RLE into buffer,     one slot per frame, only while     latch the new frame for display when
           TILES_READY ($FF0AB6)                the raster is in lines $E0-$F0:    its DMA is done (DMA_DONE $FF0AC1 clear):
           chunky frame -> NEED_SCALE ($FF0AB9) DMA buffer -> slot VRAM,           $FF0570 -> $FF0558, depth, scaled hot spot;
 2nd loop: RLE to $FF6000, scale into          clear TILES_READY + DMA_DONE,      draw the pieces at actor - camera - hot spot
           the buffer, TILES_READY              set ANIM_LOOPED ($FF0ABD)          (+128, +144), nearest actor first
```

`$FF0540+4i` holds the RLE stream (chunky) and then the DMA source; `$FF0570+4i` the header of the frame
in the pipeline, `$FF0558+4i` the header on screen (byte 0 negative = none). The frame being decoded is
`$FF04A0+2i` (offset in the set). Sprite priority is set while the actor stands on a zone cell with bit 15
(`$FF0ABB`), so it is drawn over the high-priority foreground tiles.

SAT order (`sprite_build` `$00A984`, buffer `$FF0008`, DMA'd to `$D800` every VBlank): pointer (crosshair
2×2 at `$FF06E4`, or the verb-bar cell cursor), the effect sprite (`$FF09E8` bit 4), the inventory highlight
(8 sprites), 4 fixed sprites (`$FF09EA` bit 0), **4 masking sprites** (8×32 at y `$128`/`$148`, x = 1 then
x = 0: the VDP stops drawing further sprites on those lines, so actors never cover the verb bar), then the actors.

### Palettes

The frame attribute selects the palette. Shaggy and Scooby use palettes 0/1 (`$032480`, shared, see
"Palettes" above); room actors use 1 or the room's palettes 2-3.

### Tool

    gfx.py sprite shaggy OUT.png [--anim N] [--depth D] [--scale S]   # sheet of frames (red dot = hot spot)
    gfx.py sprite 0x0642D0 OUT.png --list                             # header, animations, frame sizes
    gfx.py spritecheck DUMP.ram DUMP.vram                             # rebuild slots 0/1 tiles from RAM, compare with VRAM

Verified against the emulator (see `docs/subsystems/sprite.md`): Shaggy's and Scooby's VRAM tiles in the
Lobby, rebuilt from ROM with the RAM frame/depth values, are byte-identical.

## Tracing

`tools/patches/gpgx-vdptrace.patch` applies on top of `gpgx-cpuhook.patch`. It records the
68k source address of every DMA word (`hook_dma_src`) and exports `vram`, `cram`, `vsram` and
`reg` from the core. Build a private copy of the core with it:

    rsync -a --exclude .git ext/gpgx/ build/gpgx-mine/
    (cd build/gpgx-mine && patch -p1 < ../../tools/patches/gpgx-vdptrace.patch \
       && make -f Makefile.libretro HOOK_CPU=1)

The harness then accepts `trace NAME` / `untrace` (logs VRAM/CRAM/VSRAM writes with DMA
source or CPU PC, plus ROM data reads with PC) and `vdp NAME` (dumps
VRAM/CRAM/VSRAM/registers). The harness header comment gives the exact line formats.
