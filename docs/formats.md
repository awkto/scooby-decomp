# Asset formats: graphics compression, palettes, tilemaps

Status: these notes come from VDP write traces of the boot sequence, the title screen and the
Lobby (GPGX harness, see "Tracing" below), plus reading the 68k code. Every format described
here is checked by `tools/py/gfx.py`, which rebuilds the screens from ROM data alone. ROM
ranges are in `data/assets.txt` (generated by `gfx.py assets`).

All addresses are ROM offsets (= 68k addresses) unless they start with `$FF` (work RAM) or are
called VRAM/CRAM.

## How graphics reach the VDP

Nearly everything takes one of two routes:

1. ROM → decompressor → RAM buffer → VRAM. The buffer is usually `$FF4000` (LZSS) or
   `$FF3000` (RLE). The buffer is then written to the data port by `loc_00992C`, or DMA'd by
   `loc_0099F6`.
2. ROM → VRAM directly, uncompressed: nametable rows through `loc_00992C`, single words
   through `loc_009964`.

VDP helper routines:

| addr | purpose | args |
|---|---|---|
| `$00992C` | CPU copy to VRAM | d0 = VRAM addr, a0 = src, d1 = word count |
| `$009964` | write one VRAM word | d0 = VRAM addr, d1 = value |
| `$0099F6` | VRAM DMA from 68k bus, split at 128 KiB boundaries; calls `$009A3C` | a0 = src, d0 = VRAM dest, d1 = words |
| `$009B10` | CRAM DMA | same args as `$009A3C` |
| `$009BE4` / `$009C1E` | fill VRAM / CRAM with a word | d0 = addr, d1 = count, d2 = value |
| `$009C58` / `$009C5E` | clear VRAM / CRAM | d0 = addr, d1 = count |
| `$009E7E` | fade the 64-word palette at a0 into CRAM: 8 steps, target buffer `$FF06F8` DMA'd each frame | a0 = 128-byte CRAM image |
| `$00974C` / `$009742` | wait 1 / d0+1 VBlanks | |

Palettes always go through the RAM copy `$FF06F8` (current) / `$FF0778` (target) and reach
CRAM by DMA from `$FF06F8`. As a result, CRAM never reads from ROM directly in the traces.

## Compression format 1: LZSS (`$0097AA`)

`a0` = compressed stream, `a1` = 4 KiB ring buffer (the game always passes `$FF3000`),
`a2` = output. On return, `(a1).l` holds the decompressed size. The routine saves and restores
every register.

* The bitstream is MSB-first over big-endian data, starting at `a0`. The 68k pre-loads one
  long, then refills 16 bits at a time; logically it is a plain continuous bitstream.
* Each token starts with a flag bit:
  * `1`: an 8-bit literal. Output it and also store it in `ring[r++]`.
  * `0`: a 12-bit ring position `P`. **`P == 0` ends the stream.** Otherwise a 4-bit `L`
    follows. Copy `L + 2` bytes from `ring[P], ring[P+1], …` (mod 4096) and store each byte in
    the ring as well.
* The ring write index `r` starts at **1**, and indices wrap at 4096. The ring is never
  cleared. No stream checked so far reads an unwritten slot, so `gfx.py` starts with a zeroed
  ring.

This is classic Okumura-style LZSS (N=4096, F=17, THRESHOLD=1) with a 1-bit flag per token
instead of flag bytes, and position 0 used as the end marker. In ROM, each room asset stream is
preceded by a big-endian `u32` holding its packed length. The loader skips it with
`tst.l (a0)+`.

Verified: the Lobby tiles (`$11CB6E` → 0x6200 bytes) are byte-identical to VRAM
`$0000-$61FF` in the emulator. The three Lobby name tables match the VRAM nametable words.
All 51 rooms of both mysteries decompress to exactly `w*h*2` bytes of names.

## Compression format 2: RLE / PackBits variant (`$009C64`)

`a0` = stream, `a2` = output. Used by the title screen.

```
u32 unpacked_size
repeat until unpacked_size bytes have been produced:
  c = next byte
  c in 0x00..0x7F : copy the next c+1 bytes
  c in 0x80..0xFF : repeat the next byte ((-c) & 0xFF) + 1 times   (0xFF -> 2, 0x80 -> 129)
```

The 68k code fills the runs with long writes and then rewinds `a2`, so it may overwrite up
to 3 bytes past the run (harmless). It also sets VDP register 12 bit 3 (shadow/highlight)
while it runs if `$FF09ED` bit 3 is set. That is a side effect, not part of the format.

Verified: the title-screen font streams (`$016D38` → VRAM `$B900`) and the plane-A animation
frames match VRAM.

## Tiles, names, palettes

These are standard Mega Drive formats:

* **Tiles:** 8×8 at 4 bpp, 32 bytes, high nibble = left pixel.
* **Name (nametable) word:** `p cc v h nnnnnnnnnnn` (priority, palette 0-3, vflip, hflip,
  tile index).
* **Palette word:** hardware CRAM format `0000 BBB0 GGG0 RRR0`. CRAM images in ROM are 64
  words (4 palettes × 16 colours). Colour 0 of each palette is transparent.
* **Colour levels:** `gfx.py` maps the 3-bit levels to 0,36,73,…,255. GPGX's RGB565 output
  uses 0,32,64,96,136,168,200,232 for R/B (G slightly different).
  `tools/py/cmpshot.py` compares images in 3-bit level space, so this difference doesn't matter.

## Rooms

### Mystery ("world") headers

`$031AF2` holds 2 longs: the header pointers for mystery 0 (`$0FCA0C`, Blake's Hotel) and
mystery 1 (`$0FCA40`, Ha Ha Carnival). The index is in `$FF06AA`. The active header pointer
is kept in `$FF068E`. Every header field is an absolute long:

| off | name in gfx.py | meaning |
|---|---|---|
| +00 | state_start | initial game-state block, copied to `$FF2A00` up to +04 (`loc_007F22`) |
| +04 | state_end | |
| +08 | rooms | room table, 0x14 bytes per room, indexed by (room − 2) |
| +0C | tiles_base | base for the room-entry tile offsets |
| +10 | maps_base | base for the room-entry map-pack offsets |
| +14 | palettes | per-room palettes, 128 bytes per room, indexed by (room − 2) |
| +18, +1C | ? | not yet decoded |
| +20 | names_base | base for the room-name string offsets (e.g. `"The Lobby"`) |
| +24..+2C | ? | |
| +30 | start_room | pointer to a word: the initial `$FF06AC` |

The number of rooms is `(tiles_base − rooms) / 0x14`: 21 rooms in mystery 0, 30 in mystery 1.
Room numbers (as stored in `$FF06AC`) start at 2.

### Room entry (0x14 bytes)

| off | meaning |
|---|---|
| +00 | name offset (+ header `names_base`); the loader stores the absolute pointer in `$FF06D2` |
| +04 | tile offset (+ `tiles_base`): `u32 packed_len` followed by an LZSS stream; output goes to VRAM `$0000` |
| +08 | map-pack offset (+ `maps_base`) |
| +0C, +10 | not yet decoded (small increasing offsets, probably object/script tables) |

### Map pack

```
u16 width, u16 height      (cells, e.g. Lobby 64 x 19; copied to $FF06C6/$FF06C8)
u32 len1, LZSS[len1]       plane B names  (width*height words) -> RAM $FF7000 -> $FFA800
u32 len2, LZSS[len2]       plane A names                      -> RAM $FF8C00 -> $FFC400
u32 len3, LZSS[len3]       per-cell word map, not graphics; in the Lobby it outlines the
                           floor (values 1-6, 30, 57), probably walk/zone ids -> RAM $FFE000
u32 len4 ...               further room data (pointer kept in $FF0692; scripts/objects, not decoded)
```

In the Lobby, plane B words use palette 2 with priority clear, and plane A words use palette 3
with priority set. Across all 51 rooms, both planes mix palettes 0-3 and both priorities, and
plane A is empty in 10 rooms. `gfx.py` therefore composites in VDP order: B low, A low, B high,
A high.

### Palettes

* CRAM palettes 0-1 come from `$032480` (32 words). They are shared by all rooms and hold
  the UI, Shaggy and Scooby colours.
* CRAM palettes 2-3 are `palettes + (room−2)*128 + 0x40` (32 words), copied to `$FF07B8`.
* The first 0x40 bytes of each 128-byte per-room block are not used by the load path traced
  here. They may be alternative palettes for lights off or a fade.

### Room loader (code around `$0075B0`-`$007860`)

The loader runs these steps in order:

1. Decompress the tiles to `$FF4000`, then write them to VRAM `$0000`. The size is stored in
   `$FF3000` (minimum 0x400).
2. Decompress the UI/verb-bar font `$030916` and append it after the room tiles. Then add the
   raw UI tiles `$031AFA` (4 tiles), `$031B7A` (12 tiles) and `$031CFA` (8 tiles), plus one
   solid tile filled with `$1111`. The UI tile base indices are kept in `$FF0802`, `$FF06E4`,
   `$FF06E6`, `$FF06E8`, `$FF08B8` and `$FF068A`.
3. Fill the window plane `$D000` (0x400 words) with the blank UI tile.
4. Write the verb-bar names `$030016` (6 rows × 61 words, ROM stride 64 words) to VRAM `$AA80`,
   adding the tile base `$FF0802` to each word.
5. Decompress the three map chunks as described in "Map pack" above.
6. Stream the camera-visible columns, plus a one-column margin on each side, into the 64×32
   planes with `loc_009964`. Map row 0 goes to plane row 2, which is screen line 16.
   Plane A is `$C000`, plane B is `$E000`, and VRAM column = map column mod 64.

### Room screen layout at runtime (Lobby, H32 = 256×224)

| lines | content | how |
|---|---|---|
| 0-15 | room name ("The Lobby") | window plane `$D000` (VDP reg 18 = `$02`: 2 rows from the top) |
| 16-167 | room background, 32×19 cells visible | plane A `$C000` + plane B `$E000`, hscroll = `$FF07F8`/`$FF07FA` (= −camera x), vscroll = `$FF07FC`. These are written by `loc_00FC0A`. |
| 168-223 | verb bar (TAKE LOOK … USE) | HInt handler `$01006C` busy-waits for line 167, then points both planes to `$A000`, sets hscroll = `$FF0800` and vscroll 0 |

Other VRAM areas: SAT `$D800` (DMA from `$FF0008` every frame), hscroll table `$DC00`, and
sprite tiles `$F000-$FEFF`. Sprite tiles are streamed from the RAM buffers `$FF3000` and
`$FF3800` every few frames. `$FF4800` is also DMA'd every few frames to `$A300-$AA7F`, which
is rows 6-20 of the `$A000` plane. Its purpose is unknown: those rows are not on screen in
the bottom band.
Sprite graphics are a separate subsystem and are not decoded here.

Lobby specifics: mystery 0, room 16, 64×19 cells (512×152 px). After the start route, the camera
is at x = 160 (`$FF07F8` = `$FF60`).

## Tracing

`tools/patches/gpgx-vdptrace.patch` applies on top of `gpgx-cpuhook.patch`. It records the
68k source address of every DMA word (`hook_dma_src`) and exports `vram`, `cram`, `vsram` and
`reg` from the core. Build a private copy of the core with it:

    rsync -a --exclude .git ext/gpgx/ build/gpgx-mine/
    (cd build/gpgx-mine && patch -p1 < ../../tools/patches/gpgx-vdptrace.patch \
       && make -f Makefile.libretro HOOK_CPU=1)

The harness then accepts `trace NAME` / `untrace` (logs VRAM/CRAM/VSRAM writes with DMA
source or CPU PC, plus ROM data reads with PC) and `vdp NAME` (dumps
VRAM/CRAM/VSRAM/registers). The harness header comment gives the exact line formats.
